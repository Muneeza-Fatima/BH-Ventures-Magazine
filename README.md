# BH Ventures FZE LLC — Magazine, Edition 01

A print-ready corporate magazine, built as HTML and exported to PDF. No
InDesign required: the layout lives in CSS, the words live in one JSON file,
and the whole thing rebuilds with a single command.

Current state: **the complete 26-page magazine**. Ten venture pages, one
activity each. Sixteen of the seventeen picture slots are waiting on the
client's own imagery and show designed icon plates until it arrives — the book
is complete and printable either way.

**Edition 01 was redesigned after the client rejected the first look.** They
sent a reference — a property brochure — and it was the opposite of what had
been built: white pages instead of navy ones, large rounded corners, cards,
geometric sans, photographs in frames rather than bleeding off the sheet. The
whole visual system was rebuilt to it. What did *not* change: the page
geometry, the copy, and every one of the guards below.

---

## Quick start

```bash
npm install          # sharp, for image grading
npm run build        # copy -> HTML -> PDF -> fit -> space -> PDF -> ink
```

Output lands in `out/magazine/`:

| File | What it is |
| --- | --- |
| `BH VENTURES FZE.pdf` | 26 pages, 216 × 303 mm (A4 + 3 mm bleed), fonts embedded |
| `preview.html` | the same pages in a browser, no PDF reader needed |

> **Run the PDF and check steps outside Claude Code's tool sandbox.** The
> sandbox blocks Chrome's font rendering on this machine: headless Chrome still
> draws backgrounds and images but renders **no text at all**, so the PDF comes
> out silently wordless. Everything else is happy inside the sandbox.

## Adding the photography

Fourteen pictures are generated by the client. `IMAGE-BRIEF.md` has a prompt
for each one, the filename it must be saved as, and the rules that keep
generated images from announcing themselves.

```bash
# drop the files into assets/images/raw/, then:
npm run images:grade
npm run build
```

Nothing else changes. `build/build.mjs` checks at build time which graded files
exist and picks the photograph or the icon plate accordingly, so there is no
JSON to edit, no flag to remember, and no way for the book to ship with an
empty frame:

```
photography: 4 of 10 venture pages have their picture (6 showing icon plates)
```

## Changing the words

Every sentence is in **`content/copy.json`**. Nothing else needs touching —
not the HTML, not the CSS.

The build refuses to be quiet about unfinished copy. Any `[X]` placeholder is
reported on every run:

```
!  4 unresolved placeholder(s) in copy.json: [X]+  [X]h  [X]K+  [X]K+
```

Those four are the §08 "Proof" figures. The client's own draft says *"Confirm
real numbers with the client before print"*, so they are designed as visible
slots rather than quietly set to zero.

## Why it is built this way

Every guard below exists because something went wrong — in the reference PDF
the client supplied, or in one of this magazine's own proofs.

### 1. The page really is A4

The reference PDF was **793 × 1122 pt**, not A4's 595 × 842. The ratio was
exactly 96/72 — its HTML pixels had been exported as points. A printer would
have shrunk everything by a third, or printed at an odd size.

`build/verify-pdf.mjs` asserts the media box in **points** after every render,
and now also that the page count is a multiple of four for saddle-stitch.

### 2. No live transparency

The reference PDF carried **44 `/Luminosity` soft masks** and 504 transparency
groups, because its photo grading was done with CSS blend modes. Rendered
through pdf.js the hero photos came out hot pink and two pages lost their text
entirely — and **pdf.js is Firefox's built-in PDF viewer**, so that is what a
real reader would have seen.

All image grading is therefore **baked into the JPEG** by
`build/grade-images.mjs` (sharp), never done with CSS. The checker fails the
build on any luminosity mask or non-normal blend mode.

### 3. Static fonts, not variable

Chrome embeds a **variable** font as a **Type 3** font — glyphs as little
drawing programs instead of a real embedded typeface. It looks right on screen,
but Type 3 is not permitted in PDF/X-4 and prepress RIPs reject or rasterise it.

Measured both ways on this project: variable gave `Type3: 1, FontFile2: 0`;
pinning every axis in the Google Fonts request gives `Type3: 0, FontFile2: 1`.

Two families, one job each: **Poppins** for display, headings, card titles,
kickers and numerals, **Inter** for body copy. Poppins is the geometric voice
the client's reference is written in; Inter is what a paragraph at 9.5pt is
actually readable in.

This guard was the one that had drifted. The discipline was being followed —
every axis pinned, every face static — and the shipped PDF still carried
**three Type 3 fonts**, because `-webkit-text-stroke` on two components was
outlining text, which is also Type 3, and nothing measured it.
`verify-pdf.mjs` now asserts `Type3 = 0`.

It also asserts that **nothing but Poppins and Inter** is embedded. Chrome
falls back per *glyph*, silently: Poppins has no PRIME (`′`) and this book
prints `25°12′N 55°16′E` on nearly every page, so Segoe UI was being embedded
into an otherwise self-contained PDF. Each font stack now names the other
embedded family before any system font.

### 4. The copy is what the client approved

A clause went missing from §02 during layout — *"…is engineered to the same
exacting standard, and…"*. The page looked fine and read fine; it simply was
not what the client wrote, and it surfaced only when they re-sent the draft.

`content/client-draft.txt` holds the approved text verbatim and
`check-copy.mjs` compares **45 fields** against it on every build. It has since
found a second fault, in the reference file rather than the copy: two of the
client's own sentences had never been captured in the draft file at all.

Typographic quotes are substituted at build time — `Let's` becomes `Let’s` —
because a straight tick set at 92 pt is the loudest sign a document was typed
rather than typeset. It changes no words, and `check-copy` normalises quotes on
both sides before comparing, so the guard still sees the client's text exactly.

### 5. Space is measured, not eyeballed

The client's sharpest note was *"spaces ka laazmi khayal rakhna"*, and the
sample earned it: the bottom third of The Opening was empty, and so was the
foot of every venture page. Nobody chose those gaps.

`build/check-space.mjs` finds the deepest untouched block on every page and
fails above 28 mm. It took two attempts to make it honest:

- the probe was written one directory above the page, so **no CSS loaded at
  all** and it was measuring an unstyled document — which gave a clean bill of
  health to a page with a 90 mm hole in it;
- a full-height navy sidebar and a 5% watermark both counted as "filled", so
  every venture page scored perfectly while its text column sat empty.

It now measures the middle of the live area, walks effective opacity up the
tree, and starts its scan below the page head. Run against the old sample it
correctly reports the 51 mm hole the client saw.

The redesign is where this check earned its keep. Rebuilding every page broke
the old device that filled the holes — a navy block that ran off the bottom
edge — and check-space immediately found **twelve** pages with 50 to 115 mm of
nothing in them. The fix was not to raise the threshold. Each page was given
something real to grow into: a card grid that stretches its rows, a quote card
that grows and centres its sentence, a photograph that gets taller. The book
now reports 8–11 mm on every page **at the original 28 mm bound**.

### 6. Nothing runs under the folio

`.page` has `overflow: hidden`, so a page that is too long clips silently at
the paper edge rather than at the margin. `build/check-fit.mjs` measures every
page in the browser and now names the offending element:

```
page 21  content runs 1.6mm past the margin   <- p.value__closing
```

### 7. Light, but not white — and how that check was wrong twice

`check-ink.mjs` counts navy coverage. Its history is worth keeping:

1. Bounds set at 20–35% per page from judgement.
2. Lowered to 12% when two pages read 13% and 18%. That looked like honest
   calibration and was not — the screenshot was the whole browser window and
   the page filled only its top-left corner, diluting every reading about
   threefold. Cropping to the page put the same two at 23% and 31%.
3. The bounds went back to 20–35%. **They were still wrong**, and the client
   found the reason first. Demanding 20% navy on a page of three paragraphs and
   a quote leaves exactly one way to get it: put a navy box round something.
   That is what produced the box behind *"Ten disciplines. One standard."* —
   the device the client called *bohot bura*.

It now measures what the brief actually said. Per page, a wide band that
catches a page gone blank or accidentally black. Per book, the mean across the
pages whose colour comes from the design, plus a count of light and dark pages
so a book that is half blank and half black cannot average its way to a pass.

**The redesign did not move these bounds either**, which was not the
expectation going in — a white book was expected to need a lower floor. It did
not, because the navy did not leave, it changed shape: header bands and foot
panels instead of full-bleed blocks and sidebars. Two pages did fail, and both
were real faults rather than a bound being wrong. The imprint page measured
53% and the contact page 55% — each had a navy panel set to grow into whatever
space was left, so "the leftover" and "how dark this page is" were the same
number. The opening page measured 5.5%, carrying no navy at all. All three
were rebuilt. The book now sits at **20.9% mean, 13.7–27.1% per page**.

One thing to know when the photographs land: pages 10–19 currently read ~46%
because the icon plate standing in for each missing picture is a large navy
rectangle. They are exempt from the gate — their colour comes from the
picture, not the design — so nothing moves when real images replace them.

Its crop was also changed. It used to find the page inside the screenshot by
looking for the last pixel that was not pure white, which does not find the
page, it finds the last *content* pixel — fine on a busy dark page, and
unbounded on a page deliberately empty at the foot, which is the whole point
of the light design. It now crops by geometry: 612 × 859 pt at the known
shoot scale.

## Before this goes to a printer

1. **Attribution for the two photographs.** CC BY 2.0 requires it in the
   published work. One line in the page 2 colophon — wording is in
   `CREDITS.md`.
2. **The four §08 figures** are still `[X]`. The build warns on every run.
3. **§04 says "Nine services"** while ten are listed, and §02 and §06 both say
   *ten disciplines*. Kept exactly as the draft reads, because the instruction
   was word-for-word. One word in `copy.json` once the client confirms.
4. **Confirm `info@bhventures.ae` and `bhventures.ae`** are live.
5. **Trade licence number**, if it should appear in the colophon.
6. **§05 has no leadership names, bios or portraits.** The page is built to
   receive them.
7. **Convert to CMYK** (FOGRA39 / ISO Coated v2) and use a rich black for the
   navy — **C 90 · M 75 · Y 45 · K 70**, which lands at 280% total ink, inside
   the 300% sheet-fed limit. Flat K-only navy prints patchy.
8. **Aqua `#2DD4C0` dulls in CMYK.** Either accept it, or run it as Pantone
   3255 C — a fifth colour, more money, exact on press. It appears only on
   navy, so the quantity is small.
9. **The cover photograph is a placeholder.** It falls back to
   `cover-burj-night.jpg`, a night frame kept from the dark design. The light
   cover was built for a bright morning frame — see `cover-dubai-hero.jpg` at
   the top of `IMAGE-BRIEF.md`. It prints correctly either way.
